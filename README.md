# MetaML Workbench

MetaML Workbench is a model-driven development platform for authoring BPMN 2.0 process models and generating dedicated, executable Spring Boot Target Platform applications.

The Workbench provides visual process modeling, automated code generation, capability and governance integration, and a managed runtime for executing synchronized Proxy/Twin processes.

---

## Architecture at a Glance

The core MetaML lifecycle transitions from visual modeling to executable microservices:

```
+-------------------------------------------------------------+
|                        MetaML UI                            |
|             (React + bpmn-js Modeling Canvas)               |
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|                   MetaML Workbench API                      |
|           (Process Storage, Validation, Codegen)            |
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|             Generated Spring Boot Target Platform           |
|      (Camunda 7 Process Engine + Pluggable Capabilities)     |
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|                    Proxy / Twin Runtime                     |
|           (AMQP Event Synchronization via RabbitMQ)         |
+-------------------------------------------------------------+
```

1. **Model BPMN**: Author or import standard BPMN 2.0 XML workflows in the browser.
2. **Generate Target Platform**: Transform process models into a separate Spring Boot Target Platform application scaffolded from the canonical template.
3. **Launch**: Run and supervise the generated Target Platform on a dynamic port via the Workbench process manager.
4. **Proxy/Twin Runtime**: Execute correlated Proxy and Twin process activities synchronized through RabbitMQ messaging.

## Requirements

- **Java JDK 24 or newer**: Required to build and run the Workbench backend services (`wbapi`, `workbench`, `nodemanager`).
- **Java JDK 24 target**: Target Platforms generated by the Workbench compile and run on Java 24 (Spring Boot 4.1.0, Camunda 7.24.0).
- **Node.js (v18+) and npm**: Required for the React frontend application.
- **Git**: Required for version control.
- **Docker**: Recommended for running RabbitMQ as a local container.
- **RabbitMQ**: Required when using Proxy/Twin AMQP synchronization in generated Target Platforms. It is not required for basic Workbench startup, modeling, generation, or Target Platforms that do not use runtime messaging.
- **Maven**: The repository provides the Maven Wrapper (`mvnw`, `mvnw.cmd`) in `backend/` and inside every generated Target Platform. A system Maven installation (`mvn`) on `PATH` or configured via `MAVEN_HOME` is used as a fallback if launching an unbundled project.

## Quick Start

### 1. Backend (REST API)

The backend service (`wbapi`) runs on port 8082 and provides the Workbench REST API.

#### Initial Build (Fresh Clone)

On a fresh clone, install the backend modules into your local Maven cache so that shared libraries (`capability-core`, `reference-providers`, `workbench`) are available to dependent modules:

- **Windows PowerShell:**
  ```powershell
  cd backend
  .\mvnw.cmd install -DskipTests
  ```
- **Linux / macOS:**
  ```bash
  cd backend
  ./mvnw install -DskipTests
  ```

*(On Windows, `.\run-wbapi.cmd` is also available as a convenience launcher to run the installation and start the backend).*

#### Normal Startup

Start the `wbapi` service:

- **Windows PowerShell:**
  ```powershell
  cd backend
  .\mvnw.cmd -pl wbapi spring-boot:run
  ```
- **Linux / macOS:**
  ```bash
  cd backend
  ./mvnw -pl wbapi spring-boot:run
  ```

Verify the backend is running: [http://localhost:8082/api/v1/projects/all](http://localhost:8082/api/v1/projects/all)

---

### 2. Frontend (Web Interface)

The React web application runs on port 3000.

```bash
cd frontend
npm install
npm start
```

Open [http://localhost:3000](http://localhost:3000) in your browser.

---

### 3. Node Manager (Optional - for Evolve & Agent Catalog)

The Node Manager service (`nodemanager`) runs on port 8083 and acts as a capability catalog stub for dynamic agent discovery and Evolve features. It is optional for basic process modeling, generation, and launch.

To start Node Manager:

- **Windows PowerShell:**
  ```powershell
  cd backend
  .\mvnw.cmd -pl nodemanager spring-boot:run
  ```
- **Linux / macOS:**
  ```bash
  cd backend
  ./mvnw -pl nodemanager spring-boot:run
  ```

---

### 4. RabbitMQ (Optional for Basic Modeling; Required for Proxy/Twin Runtime)

RabbitMQ provides the message broker for event-driven process coordination and Proxy/Twin synchronization in generated applications. It is optional for basic Workbench startup and process modeling, but required when running Target Platforms with runtime messaging.

Start a RabbitMQ container with the management plugin:

```bash
docker run -d --name metaml-rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:3-management
```

For subsequent runs:

```bash
docker start metaml-rabbitmq
```

Management console: [http://localhost:15672](http://localhost:15672) (credentials: `guest` / `guest`).

## Basic Workflow

1. **Project**: Create a project under **Project > Create** or select an existing project under **Project > Edit**.
2. **Model**: Open the BPMN canvas under **Transmute > Model**. Design a new workflow or click **Open BPMN file** to load an existing BPMN 2.0 XML file.
3. **Save**: Click **Save** in the toolbar. Saving updates the model under its existing logical ID and registers a new process definition version with the engine.
4. **Generate**: Navigate to **Transmute > Generate**. Locate the saved process model and click **Generate** to scaffold a complete Spring Boot Target Platform.
5. **Launch**: Navigate to **Transmute > Launch** to manage and execute the generated application.

## Launching a Target Platform

The **Transmute > Launch** dashboard provides managed process execution for generated Target Platforms:

```
Generated / Stopped
        |
      Launch
        |
      Running
        |
[Open Platform] [Open Cockpit] [Stop]
```

- **Launch**: Starts the generated Target Platform as a supervised child JVM on an automatically selected free port. Launch initiates background startup and does not automatically redirect the browser.
- **Running State**: Once the target application passes health checks and begins listening, the status updates to `Running` and exposes direct actions:
  - **Open Platform**: Explicitly opens the root URL of the running Target Platform in a new browser tab (`http://127.0.0.1:<port>/`).
  - **Open Cockpit**: Explicitly opens the Camunda Cockpit operational dashboard (`http://localhost:<port>/camunda/app/cockpit/engine/`).
  - **Stop**: Explicitly terminates the application process tree and releases the assigned network port.
- **Runtime Details**: Expanding a running project row displays active runtime information (such as process keys, listening port, and business key) without duplicated navigation controls.

## Running a Generated Target Platform Separately

Each generated Target Platform is a separate Spring Boot application configured with Camunda BPMN engine and AMQP messaging.

Generated applications bundle their own Maven Wrapper (`mvnw`, `mvnw.cmd`, `.mvn/wrapper/`).

### Output Directory Locations

- **Runtime Generated Applications**: By default, applications generated from the Workbench backend are written to `../generated-target-platforms/` (a sibling directory located outside the Workbench repository root).
- **Tracked Reference Platforms**: The repository also includes sample pre-generated platforms in `generated-target-platforms/` (such as `redcollar-manufacturing` and `liveverify-wiretransfer`).

### Dependencies

Generated Target Platforms depend on MetaML modules (`capability-core` and `reference-providers`). On a fresh clone, run `mvnw install -DskipTests` in `backend/` before compiling a generated project so these dependencies are present in `~/.m2/repository`.

### Execution via Maven Wrapper

1. Navigate to the generated application directory:
   ```bash
   cd <path-to-generated-project>
   ```

2. Compile the project:
   - **Windows PowerShell:**
     ```powershell
     .\mvnw.cmd clean compile
     ```
   - **Linux / macOS:**
     ```bash
     ./mvnw clean compile
     ```

3. Run the application:
   - **Windows PowerShell:**
     ```powershell
     .\mvnw.cmd spring-boot:run
     ```
   - **Linux / macOS:**
     ```bash
     ./mvnw spring-boot:run
     ```

4. Access the application:
   - Application root: [http://localhost:8080](http://localhost:8080) (or the port assigned via `SERVER_PORT`)
   - Camunda Cockpit: [http://localhost:8080/camunda](http://localhost:8080/camunda) (default login: `demo` / `demo`)

## Repository Structure

- `backend/`: Multi-module Maven project providing backend services:
  - `wbapi/`: Spring Boot REST API application and Workbench entry point (port 8082).
  - `workbench/`: Core modeling services, BPMN transformation, code generation, and project launcher.
  - `capability-core/`: Shared capability definitions, execution contexts, and output contracts.
  - `providers/`: Reference component executor implementations (`artifactId: reference-providers`).
  - `nodemanager/`: Node Manager service stub for agent catalog discovery (port 8083).
  - `RedCollarTP/`: Spring Boot + Camunda template scaffold used by the project generator.
- `frontend/`: React single-page application (port 3000) using Bootstrap and `bpmn-js`.
- `generated-target-platforms/`: Tracked sample generated Target Platform applications.
- `demo/`: BPMN process fixtures, test datasets, and verification protocols.
- `docs/architecture/`: Architecture specifications, runtime diagrams, and Architecture Decision Records (ADRs).
